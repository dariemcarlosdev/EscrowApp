# v1.1 Release Roadmap — Advanced Webhook Patterns

> **Status:** Planning (post-MVP)  
> **Estimated Timeline:** 4-6 weeks after MVP release  
> **Scope:** Event reliability, audit compliance, advanced state management  
> **Previous Release:** MVP — Observational Webhook Handler

---

## Executive Summary

After the MVP webhook handler ships (Track C complete), v1.1 addresses production needs:

1. **Event Deduplication** — Stripe retries cause duplicate events; database-backed cache eliminates this
2. **Event Sourcing** — Store all state changes; enables regulatory audit trails and timeline reconstruction
3. **Outbox Pattern** — Guarantee domain event delivery; survives process crashes

**Release Goals:**
- ✅ Zero duplicate events in production
- ✅ Complete audit trail (reconstruct any transaction timeline)
- ✅ Event delivery guarantees (no loss on crash)
- ✅ Regulatory compliance for payment events

### Phase 2: Event Sourcing (Weeks 3-4)

**Why Second:** Foundation for audit trail; enables regulatory compliance; enables Dead Letter Queue.

**Design:**

Instead of:
```csharp
UPDATE EscrowTransaction SET Status = 'Held'
```

Use:
```csharp
INSERT INTO PaymentEvents (TransactionId, EventType, Timestamp, Payload, Actor)
VALUES (42, 'PaymentHeld', NOW(), '{...json...}', 'HoldFundsCommand')

-- Compute Status: SELECT event_type FROM PaymentEvents WHERE transaction_id = 42 ORDER BY id DESC LIMIT 1
```

**Tasks:**

### Phase 3: Outbox Pattern (Weeks 5-6)

**Why Third:** Ensures domain event delivery; prerequisite for distributed systems (v1.2+).

**Design:**

```
Synchronous (DB Transaction):
  1. Save transaction → INSERT EscrowTransaction
  2. Save events → INSERT PaymentEvents
  3. Save outbox entry → INSERT OutboxEvents (Published = false)
  COMMIT

Asynchronous (Background Service):
  - Poll OutboxEvents WHERE Published = false (every 100ms)
  - For each row: publish to IEventBus
  - Mark Published = true
```

**Tasks:**

| ID | Task | Effort | Dependencies | Acceptance Criteria |
|----|------|--------|--------------|-------------------|
| tc-14a | Create `OutboxEvents` table schema | 1 day | — | Migration: (id PK, transaction_id FK, event_type, payload JSON, published, created_at, published_at) |
| tc-14b | Create `OutboxPublishingService` (background) | 2 days | tc-14a | Service: IHostedService, polls table every 100ms, publishes to IEventBus |
| tc-14c | Modify handlers to append to OutboxEvents | 2 days | tc-14a, tc-14b | Update all handlers to INSERT INTO OutboxEvents (same transaction) |
| tc-14d | Add health check (outbox lag monitoring) | 1 day | tc-14a, tc-14b | Health endpoint: /health/outbox → returns lag (max published_at - now) |
| tc-14e | Write `OutboxIntegrationTests` | 2 days | tc-14a, tc-14b, tc-14c | Tests: process crash, restart, verify event published exactly once |
| tc-14f | Update documentation | 1 day | tc-14a, tc-14b | Create `docs/platform/architecture/patterns/outbox-pattern.md` |

## Post-Phase 3 (v1.2+)

These patterns are deferred but planned:

### v1.2 — Long-Running Workflows

**tc-15: Saga Pattern**
- Orchestrate multi-step workflows (dispute resolution with compensation)
- Example: DisputeRaisedEvent → ComplianceCheck → RefundApprovedEvent or RefundDeniedEvent
- Effort: 10-15 days

**tc-16: Dead Letter Queue**
- Capture unprocessable events for investigation
- Example: Webhook for deleted transaction → DLQ for manual review
- Effort: 2-3 days

### v1.3+ — Optimization & Observability

**tc-17: Event Enrichment**
- Add context to events at publish time (customer name, service description)
- Reduce N+1 dashboard queries
- Effort: 1-2 days

**tc-18: Circuit Breaker (Advanced)**
- Provider health dashboards
- Automatic failover to backup provider
- Effort: 2-3 days

## Risk Mitigation

| Risk | Mitigation |
|------|-----------|
| Event Sourcing query perf degradation | Add indexes on (transaction_id, event_type); test with 10K+ events before release |
| Outbox polling overhead | Batch polling (load 100 at a time); tune interval from 100ms if needed |
| Backward compatibility | All changes are additive (Status still exists, computed from events) |
| Data migration | Event Sourcing requires backfill; plan 2-hour maintenance window |
| Testing complexity | Add integration tests covering crash scenarios; use WebApplicationFactory |
